# 指尖血糖仪蓝牙协议（罗氏 Accu-Chek）

手机 App「手环血糖」绑定罗氏蓝牙血糖仪、读取指尖血糖记录所用的协议。
来源是罗氏官方微信小程序「轻糖生活」（appid `wx440a980df1fce173`，v119）：它支持的四款血糖仪全部走蓝牙联盟标准的 **Glucose Profile（GLP 1.0）**，没有私有加密，也没有私有指令。
本文记录小程序的做法、本 App 的实现，以及两者不同的地方。实现代码在 `android/app/src/main/java/com/fch/cgmband/core/GlucoseProfile.kt`（解析）和 `MeterSession.kt`（GATT 流程）。

## 1. 支持的设备

小程序 `app.js` 模块 9861（蓝牙）和 4489（设备列表 mixin）里列出的型号：

| 型号 | 英文名 | 小程序 type |
|---|---|---|
| 罗氏卓越金采 Connect | ACCU-CHEK Performa Connect | 2 |
| 罗氏智航 | ACCU-CHEK Guide | 1 |
| 罗氏逸智 | ACCU-CHEK Instant | 3 |
| 罗氏智航觅 | ACCU-CHEK Guide Me | 4 |

广播名一般是 `meter+<序列号>`；小程序只保留名字里含 `meter` 或 `Accu` 的设备。

## 2. GATT 结构

| UUID | 名称 | 属性 | 用途 |
|---|---|---|---|
| `0x1808` | Glucose Service | — | 扫描过滤、连接后查找 |
| `0x2A18` | Glucose Measurement | Notify | 每条记录一个测量值 |
| `0x2A34` | Glucose Measurement Context | Notify | 同序号记录的餐标记（可选） |
| `0x2A52` | Record Access Control Point（RACP） | Write + Indicate | 请求记录、结束回包 |

完整 UUID 形如 `00001808-0000-1000-8000-00805F9B34FB`。这几个特征值都要求加密，所以首次使用必须先配对（bond）。

## 3. 绑定

小程序（`pkgBluetooth/pair`）：

1. `startBluetoothDevicesDiscovery({ services: ["1808"] })`，直接取搜到的**第一台**。
2. `createBLEConnection` → `getBLEDeviceServices`，找到 `1808`。
3. 对 `2A52`、`2A34`、`2A18` 开启通知。特征值需要加密，这一步触发系统配对，用户在系统弹窗里输入血糖仪上的 6 位配对码。
4. 10 秒后弹出「确定配对」，用户确认后把 `deviceId`、型号上报到轻糖生活服务器。
5. 失败时提示「绑定失败，请删除设备和手机连接后重新绑定」，即去系统蓝牙设置里删除旧配对。

本 App（`MeterLink.bind` → `MeterSession`）：

1. 按服务 `0x1808` 扫描 60 秒，**列出所有**搜到的血糖仪，让用户点选。
2. 未配对时**先配对、后连接**：不建 GATT 连接，直接 `createBond()`。系统会自己建立 LE 连接，并立即发送配对请求，用户在系统弹窗里输入血糖仪上的配对码。监听 `ACTION_BOND_STATE_CHANGED`，最多等 90 秒；血糖仪自己先发起了安全请求（状态已是 `BONDING`）时只等待，不重复发起。
3. 配对完成即视为绑定成功，在本机记下地址和名称。之后的第一次传输即使失败（血糖仪配对后可能马上停止广播），绑定也保留。
4. `connectGatt(TRANSPORT_LE)` → `discoverServices`（已配对的设备延迟 1.6 秒再发现服务，等链路重新加密），确认有 `2A18` 和 `2A52` 后立刻做第一次同步。

为什么不像小程序那样先连 GATT、订阅时再触发配对：实测智航（Guide）在"认得这台手机却拿不到加密"时，连上后 80～100 ms 就主动断开（`0x13`）。这时 GATT 还没来得及发现服务，配对请求根本发不出去。先配对能把这段时间压到最短。

### 3.1 血糖仪残留旧配对

真机遇到过：轻糖生活（微信）配对成功 2.3 秒后，手机端的配对信息被删掉（`btif_dm_remove_bond`，正好发生在微信关闭连接之后），血糖仪却还保存着这台手机的身份密钥。之后手机每次连接，血糖仪都会在发出任何配对或加密请求之前就把它断开，不管是直接连接还是先配对都一样，轻糖生活自己再连也会失败。

只能在血糖仪这头清掉旧配对，之后再绑定就成功了。App 在配对失败时会提示这一点。

## 4. 同步

小程序（`pkgBluetooth/sync`）每次都读**全部**记录，由服务器按 `<deviceId>_<序号>` 去重。本 App 在本地去重，只读新记录：

1. 连接已绑定的地址，依次写 CCCD：`2A18` 通知（`01 00`）、`2A34` 通知（有则订阅）、`2A52` 指示（`02 00`）。RACP 放在最后订阅，确保不会有记录在订阅完成前到达。
2. 往 `2A52` 写请求：

   | 场景 | 字节 | 含义 |
   |---|---|---|
   | 首次同步（小程序每次都用这个） | `01 01` | Report stored records · All records |
   | 之后的同步 | `01 03 01 <seq 低字节> <seq 高字节>` | Report stored records · ≥ · 按序号过滤，seq = 上次最大序号 + 1 |

3. 血糖仪逐条推送 `2A18`（以及紧随其后、序号相同的 `2A34`）。
4. 结束时 `2A52` 回包 `06 00 01 <code>`：`01` 成功，`06` 没有符合条件的记录（增量同步没新数据时就是这个），二者都算完成。
   `03/04/05/09`（不支持该过滤方式）时退回 `01 01` 重读全部。小程序收到 `2A52` 回包后再等 1 秒才处理；Android 在同一连接上按顺序回调，不需要等。
5. 记录写入 SQLite（主键 `(设备地址, 序号)`），**写入成功后**才推进「上次最大序号」。对照液记录和被丢弃的记录也会推进序号，避免下次重复读取。

## 5. 数据格式

### 5.1 Glucose Measurement（`0x2A18`，小端）

| 字段 | 长度 | 条件 |
|---|---|---|
| flags | 1 | bit0 有时间偏移；bit1 有浓度和样本类型；bit2 单位（0 = kg/L，1 = mol/L）；bit3 有传感器状态；bit4 后面跟上下文 |
| sequence | 2 | 记录序号 |
| base time | 7 | 年(2) 月 日 时 分 秒，血糖仪本地时间，不带时区；年、月、日为 0 表示时钟未设置 |
| time offset | 2 | bit0；有符号，分钟 |
| concentration | 2 | bit1；SFLOAT（见下） |
| type / location | 1 | bit1；低 4 位类型（1 毛细血管全血 … 10 对照液），高 4 位采样部位（1 手指 … 4 对照液，15 未提供） |
| sensor status | 2 | bit3；bit5 高于量程（HI），bit6 低于量程（LO），bit11 时间错误 |

- **SFLOAT**：高 4 位是有符号指数，低 12 位是有符号尾数，值 = 尾数 × 10^指数。`0x07FF` NaN、`0x0800` NRes、`0x07FE` +∞、`0x0802` −∞、`0x0801` 保留，这些都表示没有数值。
- **换算**：kg/L × 100000 = mg/dL，mg/dL ÷ 18.02 = mmol/L（18.02 是小程序用的系数，用它算出的值和血糖仪屏幕显示一致）；mol/L × 1000 = mmol/L。结果保留一位小数。
- **时间**：记录时间 = base time + time offset，按手机所在时区解释。小程序要求「血糖仪时间设为北京时间」，时间晚于当前时间的记录会被它的服务器拒收；本 App 遇到这种记录会在同步状态里提示用户调整血糖仪时钟。

### 5.2 Glucose Measurement Context（`0x2A34`）

| 字段 | 长度 | 条件 |
|---|---|---|
| flags | 1 | bit0 碳水；bit1 餐标记；bit2 测试者/健康；bit3 运动；bit4 药物；bit6 HbA1c；bit7 扩展 flags |
| sequence | 2 | 与对应测量值相同 |
| extended flags | 1 | bit7 |
| carbohydrate ID + 值 | 1 + 2 | bit0 |
| meal | 1 | bit1；1 餐前、2 餐后、3 空腹、4 随机（casual）、5 睡前 |

本 App 只用到餐标记，后面的字段不读。

### 5.3 RACP 回包（`0x2A52`）

`06 00 <请求的操作码> <结果码>`。结果码：`01` 成功、`02` 不支持该操作码、`03` 运算符无效、`04` 不支持该运算符、`05` 操作数无效、`06` 没有记录、`07` 中止失败、`08` 操作未完成、`09` 不支持该操作数。

## 6. 与小程序实现的差异

| 项目 | 小程序 | 本 App | 原因 |
|---|---|---|---|
| 单位标志位 | 忽略，一律当 kg/L | 按 bit2 区分 | mol/L 时小程序会把 5.6 算成 31.1；罗氏血糖仪实际都发 kg/L，平时碰不到 |
| 上下文解析 | 固定读第 4 个字节作餐标记 | 按 flags 跳过扩展 flags 和碳水字段 | 带碳水时小程序会把碳水 ID 当成餐标记 |
| 时间偏移 | 上传前加到时间上 | 同样加上 | 一致 |
| 选设备 | 取搜到的第一台 | 列出全部，用户点选 | 附近有多台血糖仪时更可靠 |
| 每次读取 | 全部记录 | 首次全部，之后按序号增量 | 少传数据；血糖仪不支持过滤时自动退回全部 |
| 对照液、HI/LO | 原样上传 | 丢弃对照液；HI/LO 保留为标记 | 对照液不是血糖 |
| 90 天限制 | 只上传 90 天内 | 全部保留在本机 | 这是轻糖生活服务器的规则 |

**待实机确认**：小程序把餐标记 `4` 归为「睡前」时段、`5` 没有专门处理，和规范（4 随机、5 睡前）不一致。本 App 按规范显示。如果实测罗氏血糖仪的「睡前」发的是 4，需要改 `Meal` 的映射。
